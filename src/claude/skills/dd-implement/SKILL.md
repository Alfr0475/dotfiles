開発フローの最終段。`plan.md` のとおりに実装する。**計画を作ったのとは別の新しいセッション**で
実行する前提（計画作成時の文脈に頼らず、計画書だけで実装できるかの確認も兼ねる）。

作業名: $ARGUMENTS

## 絶対の制約

- **リポジトリのルール（CLAUDE.md / AGENTS.md / CONTRIBUTING 等）を最優先で守る**
- 計画に無い変更をしない。「ついでに直したい」ものは実装メモに書くだけにする
- 計画と実際のコードが食い違ったら、**推測で進めずに止まって**ユーザーに確認する
- PR は作らない。コミットはユーザーの確認を取ってから行う

## 手順

### Step 1: 読む

```sh
dir="$(~/.claude/skills/_lib/design-docs-dir.sh <作業名>)"
```

- `$dir/plan.md`（無ければ止まる）と `$dir/requirements.md`
- リポジトリのルール。ブランチ名・コミットメッセージの慣習は `git log` でも確認する

### Step 2: 実装する

`plan.md` の「実装ステップ」の順に進める。テストも計画どおりに書く。

### Step 3: 品質チェック

`plan.md` の「品質チェック」のコマンドを実行する。失敗したら直す。
失敗の原因が計画の誤りなら、直す前にユーザーに確認する。

### Step 4: セルフレビューを 3 回繰り返す

差分（`git diff`）を読み、以下の観点でレビュー → 修正 → 品質チェック、を **3 回**行う。

- 受け入れ条件・計画との一致
- リポジトリのルールと既存コードの書き方への一致（命名・コメント密度・イディオム）
- バグ・異常系の漏れ
- 不要な変更・過剰な防御コード

各回で何を見つけて何を直したかを短く記録しておく。

### Step 5: 実装メモを残す

`$dir/plan.md` の末尾に追記する（リポジトリ側には書かない）。

```markdown
## 実装メモ
- 計画からの逸脱: <内容と理由。無ければ「なし」>
- セルフレビュー: <1〜3 回目で直したこと>
- 気づき: <触らなかったが気になった点>
```

### Step 6: 報告する

変更したファイル、品質チェックの結果（実行したコマンドと結果）、計画の「動作確認手順」を示し、
コミットを提案する。PR 作成とレビューはユーザーがプロジェクトのルールに沿って行う。

開発フロー（dd-requirements → dd-plan → dd-review-plan → dd-explain → dd-implement）の 1 段目。
依頼の要件を深掘りし、**事情を知らない AI エージェントが詳細な実装計画を作れるだけの情報**を
`requirements.md` にまとめる。

入力: $ARGUMENTS

## 絶対の制約

- **リポジトリには何も書かない。** 生成物はすべて保存先ディレクトリ（下記）に置く
- リポジトリのルール（CLAUDE.md 等）と矛盾する要件・決定を見つけたら、ユーザーに指摘する
- 推測で要件を埋めない。分からないことは質問するか「未決事項」に残す

## 保存先

保存先のルールは `~/.claude/skills/_lib/design-docs-dir.sh` が持つ。パスを自分で組み立てない。

```sh
~/.claude/skills/_lib/design-docs-dir.sh --list        # 既存の作業名
~/.claude/skills/_lib/design-docs-dir.sh <作業名>      # 作業ディレクトリ
```

## 手順

### Step 1: リポジトリのルールを把握する

存在するものを読む: `CLAUDE.md`（サブディレクトリのものも）/ `AGENTS.md` / `.claude/` 配下のルール /
`CONTRIBUTING*` / `README.md` / `docs/` の主要ドキュメント。
要件に関係しそうな既存コードも、この時点でざっと探しておく。

### Step 2: 要件を取得する

入力元は決め打ちしない。入力の形から判断する。

- チケット番号や URL（Jira / Redmine / Backlog / GitHub など）なら、**いま使える MCP ツールや CLI** を
  探して読む。コメント・添付・リンク先の仕様書も必要に応じて読む
- 読めない（ツールが無い・未認証・権限が無い）なら、その旨を伝えて本文の貼り付けを依頼する
- 依頼文そのものが渡されたら、それを入力とする

### Step 3: 深掘りする

- **1 回に 1 問**だけ質問する。各質問に**推奨回答とその理由**を添える
- **コードやドキュメントを読めば分かることは質問しない。** 自分で調べて結果を示す
- 曖昧な用語・境界条件・異常系・既存機能への影響・やらないこと、を重点的に詰める
- 質問ごとに、決まったことを頭の中で決定ログに積んでいく
- 「事情を知らない AI が実装計画を作れる」と判断できたら終了し、ユーザーに確認する

### Step 4: 作業名を決める

`<チケット番号>-<英小文字ケバブの要約>`（例: `CRM-1234-coupon-validation`）。
チケットが無い依頼は要約のみ（例: `coupon-validation`）。日付は付けない。

案を提示してユーザーに確定してもらう。`--list` で同名がある場合は上書きせず、
続きとして扱うか別名にするかを確認する。

### Step 5: requirements.md を書く

`mkdir -p` で作業ディレクトリを作り、`requirements.md` を以下の構成で書く。
書いたらパスを伝え、次は `/dd-plan <作業名>` であることを案内する。

```markdown
# <作業名>: <タイトル>

## 入力元
<チケット URL / 依頼者と日付 / 貼り付けた原文の要約>

## 背景・目的
<なぜやるのか。誰が何に困っているか>

## スコープ
### やる
### やらない

## 受け入れ条件
- [ ] <検証できる形で書く>

## 用語集
| 用語 | 意味 | コード上の名前 |
|---|---|---|

## 決定ログ
### R-01: <決めたこと>
- 理由:
- 却下した案:

## 関連する既存コード
- `<パス>` — <関係>

## リポジトリのルールで関係するもの
- <ルール>（出典: `<ファイル>`）

## 未決事項
- <決まっていないこと。誰に確認するか>
```

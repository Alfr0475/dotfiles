開発フローの理解確認。実装計画を**人間が自分の言葉で説明できる状態**にするための図解 HTML を作る。
AI に理解を外注しないことが目的なので、要約するだけでなく「なぜそうなっているか」を必ず書く。

引数: $ARGUMENTS（`<作業名>` または `<作業名> D-xx`）

## 絶対の制約

- **リポジトリには何も書かない。** HTML は作業ディレクトリの `explain/` に置く
- 外部公開しない（Artifact・Gist・外部サービスへのアップロード禁止）。業務コードを含むため
- 外部通信しない単一 HTML にする（CDN・Web フォント・外部画像を使わない。図はインライン SVG）
- `plan.md` に書かれていないことを事実として書かない。補足した説明はそれと分かるように書く

## 手順

### Step 1: 入力を読む

```sh
dir="$(~/.claude/skills/_lib/design-docs-dir.sh <作業名>)"
```

`$dir/plan.md` を読む（無ければ止まる）。`$dir/requirements.md` と `$dir/plan-review.md` があれば読む。
図や説明の正確さのため、`plan.md` が挙げる変更対象のコードも読む。

### Step 2: HTML を書く

同じディレクトリの `template.html` を土台にする（色・レイアウト・ライト / ダーク対応が入っている）。

**引数が作業名だけ** → `$dir/explain/index.html` を書く。構成:

1. **一言でいうと** — 何をどう変えるかを 1〜2 文で
2. **読む前に知っておくこと** — 前提となる既存の仕組み・用語（`requirements.md` の用語集を使う）
3. **全体図** — 変更するファイル / コンポーネントと処理の流れをインライン SVG で。
   変更箇所は強調色、既存のままの箇所は控えめな色にする
4. **設計判断カード** — `plan.md` の `D-xx` ごとに 1 枚。
   「何を決めたか」「なぜそうなっているか」「却下した案」を書く
5. **変更対象ファイル** — 表で。ファイルごとに 1 行で役割
6. **理解チェック** — 自分の言葉で説明できるか試す問いを 3〜5 個。
   「なぜ〜ではなく〜なのか」「〜の場合はどう動くか」の形にし、答えは `<details>` で折りたたむ

**`D-xx` が指定された** → `$dir/explain/D-xx.html` を書く。構成:
判断の背景 / 関係するコード（抜粋とファイル:行）/ 処理の流れ（SVG）/ 却下した案との比較表 /
この判断が崩れる条件 / 理解チェック。
あわせて `index.html` の該当カードに深掘りページへのリンクを足す。

### Step 3: 開く

`open <書いた HTML のパス>` で開き、パスを伝える。
質問があれば答え、分かりにくかった点は HTML に反映する。
理解できたら、新しいセッションで `/dd-implement <作業名>` を実行するよう案内する。

開発フローの 2 段目。`requirements.md` を元に、**別セッションの AI がそれだけ読めば迷わず実装できる**
実装計画 `plan.md` を作る。

作業名: $ARGUMENTS

## 絶対の制約

- **リポジトリには何も書かない。** 計画は作業ディレクトリに置く
- **推測で書かない。** ファイル・関数・API・コマンドはすべて実物を確認してから書く。
  確認できなかったものは `<!-- 要確認 -->` と明記する
- リポジトリのルールに従った計画にする。ルールと要件が衝突したら書く前にユーザーに確認する

## 手順

### Step 1: 入力を読む

```sh
dir="$(~/.claude/skills/_lib/design-docs-dir.sh <作業名>)"
```

`$dir/requirements.md` を読む。無ければ止まり、先に `/dd-requirements` を案内する
（作業名の候補は `--list` で示す）。`$dir/plan.md` が既にあれば、上書きか改訂かを確認する。

### Step 2: リポジトリを調べる

- ルール: `CLAUDE.md`（サブディレクトリも）/ `AGENTS.md` / `.claude/` / `CONTRIBUTING*` / lint・formatter 設定
- 変更対象になるコードと、その呼び出し元・テスト
- 品質チェックのコマンド: `package.json` の scripts / `Makefile` / `composer.json` / CI 設定などに
  **実際に定義されているもの**
- 使うライブラリの API は、リポジトリで使っているバージョンのドキュメントか実コードで確認する

### Step 3: plan.md を書く

以下の構成で `$dir/plan.md` を書く。設計判断は `D-01` から連番を振る（`/dd-explain` がカードにする）。

````markdown
# <作業名>: 実装計画

## 概要
<何をどう変えるか。3〜5 行>

## このリポジトリのルール
- <守るべき規約>（出典: `<ファイル>`）

## 設計判断
### D-01: <決めたこと>
- 判断:
- 理由:
- 却下した案と理由:

## 変更対象ファイル
| ファイル | 種別 | 変更内容 |
|---|---|---|
| `<パス>` | 新規 / 変更 / 削除 | |

## 実装ステップ
1. <順序に意味があるなら理由も>
   - 変更箇所（必要なら before / after のコード）

## 使う API・ライブラリ
- `<API>` — <正確な書き方>（参照: <URL またはファイル:行>）

## テスト方針
- 対象 / 配置先 / 観点（正常系・異常系・境界値）

## 品質チェック
```sh
<リポジトリで実際に定義されているコマンド>
```

## 動作確認手順
1. <手で確かめる手順と期待結果>

## 受け入れ条件との対応
| 受け入れ条件 | 満たす箇所 |
|---|---|

## 未決事項・リスク
````

### Step 4: 案内する

パスを伝え、次の選択肢を案内する:

- `/dd-review-plan <作業名>` — 計画を別エージェントにレビューさせる
- `/dd-explain <作業名>` — 図解 HTML で自分の理解を確かめる

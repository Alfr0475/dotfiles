開発フローの計画レビュー。計画を書いた文脈に引きずられないよう、**会話を共有しない別エージェント**に
`plan.md` をレビューさせる。指摘をそのまま反映せず、**採否はユーザーが決める**。

作業名: $ARGUMENTS

## 絶対の制約

- リポジトリには何も書かない
- レビュー担当には計画作成時の会話や経緯を渡さない（ファイルのパスだけ渡す）
- 指摘を勝手に反映しない。ユーザーが採用したものだけ反映する

## 手順

### Step 1: 入力を確認する

```sh
dir="$(~/.claude/skills/_lib/design-docs-dir.sh <作業名>)"
```

`$dir/requirements.md` と `$dir/plan.md` が無ければ止まる。
`$dir/plan-review.md` があれば読み、過去に却下した指摘を把握しておく。

### Step 2: レビューを依頼する

`general-purpose` サブエージェントを起動し、以下だけを渡す（リポジトリのルートパスは実際の値に置き換える）。

```
実装計画のレビューを依頼します。コードの変更はしないでください。

- 要件: <$dir/requirements.md>
- 実装計画: <$dir/plan.md>
- 対象リポジトリ: <リポジトリのルート>
  （CLAUDE.md / AGENTS.md などリポジトリのルールも読んでください）

観点:
1. 要件・受け入れ条件の満たし漏れ
2. 実際のコードとの不整合（存在しないファイル・関数・API、誤った前提）
3. テスト方針の不足（必要なケースの漏れ、テスト不能な設計）
4. リポジトリのルール違反
5. 過剰な設計（不要な防御コード、要件外の変更、将来のための抽象化）

各指摘を次の形式で返してください。根拠の無い指摘は不要です。
- 番号 / 重要度（高・中・低）/ 該当箇所（plan.md の節）/ 指摘 / 根拠（ファイル:行 など）/ 修正案
```

### Step 3: 仕分けする

返ってきた指摘を自分で検証し（根拠のファイルを実際に読む）、各指摘に**採否の推奨と理由**を付ける。
過剰な防御や要件外の提案は「不採用推奨」とする。過去に却下済みの指摘も同様。

`$dir/plan-review.md` に追記する（既存の内容は消さない）。

```markdown
## レビュー <N> 回目

| # | 重要度 | 箇所 | 指摘 | 推奨 | 理由 | 採否 |
|---|---|---|---|---|---|---|
| 1 | 高 | 実装ステップ 2 | | 採用 | | 未定 |
```

### Step 4: 採否を決めてもらう

表を示し、ユーザーに採否を決めてもらう。決まったら:

- 採用した指摘だけ `plan.md` に反映する
- `plan-review.md` の「採否」列を更新する（不採用は理由も残す）

最後に、もう一度レビューするか（`/dd-review-plan` の再実行）、`/dd-explain` で理解確認に進むかを案内する。

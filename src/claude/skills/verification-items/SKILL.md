Jira チケットに貼り付ける検証項目を作成する。出力先は Jira のため、Markdown の表や見出しではなく**箇条書き**で組み立てる。

## 出力形式

- 箇条書きで書く
- 大きい項目から小さい項目へネストする
- **一番ネストされた末端の内容は、チェック項目と同義になるように記載する**
- **末端の項目は 1 項目で 1 つのチェックになるようにする**。複数の確認を 1 行に詰め込まない
- 必要があれば検証観点の前に対応内容の概要を記載する

## 項目構成

次を参考にする。記載する必要がない項目は削除してよい。必要に応じて項目は増減してよい。

```
・概要
・検証観点
　・検証対象
　・検証対象画面
　・共通する前提条件
　・テスト観点
　　・修正確認
　　　・画面名（URL）
　　　　・観点名
　　　　　・前提条件
　　　　　・手順
　　　　　・確認項目
　　・デグレ確認
　　　・画面名（URL）
　　　　・観点名
　　　　　・前提条件
　　　　　・手順
　　　　　・確認項目
```

## テスト観点の書き方

- **各項目の一番上は画面名と URL を起点にする**
- その下に観点名を置き、観点ごとに前提条件・手順・確認項目の 3 つを書く
- 「修正確認」は今回の変更で新しく期待される挙動を確認する項目
- 「デグレ確認」は今回の変更で壊れていないことを確認する項目。変更箇所が影響しうる既存機能を洗い出して並べる

## 前提条件の書き方

前提条件は共通と個別の**二段構え**にする。

- 全項目に共通するものだけを「共通する前提条件」に置く。権限・リリース状態・キャッシュ削除など
- 項目ごとに必要なものは各観点の「前提条件」に書く。対象データの状態、用意する画像など
- **手作業で用意できない規模のデータは「開発担当が用意していること」と明記する**。例：コンテンツパートが 200 個登録された記事
- 検証担当が実際に操作して作る分は前提に含めない。例：199 個を開発担当が用意し、200 個目は検証担当が追加する

## 手順の書き方

- **各項目の手順は独立して完結させる。共通手順としてまとめたり、他項目を参照したりしない**
- ログインなど毎回同じ操作になるものも省略せず各項目に書く
- 番号付きで書く
- 操作は**画面上のボタン名・ラベルをそのまま使う**。そのために Blade を読んでラベルを確認する
- 同一項目内での繰り返しに限り「手順 3 から手順 5 を繰り返す」と参照してよい

## 確認項目の書き方

- **手順番号を参照しない**。「手順 3 で保存が成功すること」ではなく「200 個の状態で保存が成功すること」と書く
- 1 項目 1 チェックにする

## 作成前に押さえること

1. 実装差分を確認し、**変更が影響する画面をすべて洗い出す**（管理画面・フロント PC・フロント SP・プレビュー等）
2. 画面ごとに URL を確定させる
3. Blade を読み、手順で使うボタン名・入力欄のラベルを確認する
4. 境界値・異常系のうち、検証担当者が手で再現できるものを項目にする。再現に開発者の手が要るもの（curl での不正リクエスト等）は含めず、実装側の検証結果として PR に残す

## 出力例

```
・概要
　・読みもの記事のコンテンツパートの上限を 100 個から 200 個に変更した

・検証観点
　・検証対象
　　・読みものブログ記事の作成・編集・表示
　・検証対象画面
　　・管理画面 記事検索（/blog-article/search）
　　・管理画面 記事編集（/blog-article/{id}/update）
　　・フロント 記事詳細 PC（/blog/{id}/detail）
　・共通する前提条件
　　・管理画面に staff 以上の権限でログインできること
　　・検証環境に本対応がリリースされていること
　　・検証開始前にブラウザのキャッシュを削除していること

　・テスト観点
　　・修正確認
　　　・管理画面 記事編集（/blog-article/{id}/update）
　　　　・コンテンツパート数の上限
　　　　　・前提条件
　　　　　　・コンテンツパートが 199 個登録された日本語の下書き記事を開発担当が用意していること
　　　　　・手順
　　　　　　・1. 管理画面にログインする
　　　　　　・2. 記事検索（/blog-article/search）から対象の記事を検索し「編集」を押す
　　　　　　・3. 画面下部の「本文」を押し、入力欄に内容を入力して入力欄の「保存」を押す（合計 200 個）
　　　　　　・4. 「下書き保存」を押す
　　　　　　・5. 記事検索から同じ記事を開き直す
　　　　　　・6. 画面下部の「本文」を押し、入力欄に内容を入力して入力欄の「保存」を押す（合計 201 個）
　　　　　　・7. 「下書き保存」を押す
　　　　　　・8. 記事検索から同じ記事を開き直す
　　　　　・確認項目
　　　　　　・コンテンツパートを 200 個目まで追加できること
　　　　　　・コンテンツパートが 200 個の状態で保存が成功すること
　　　　　　・保存後に記事を開き直すとコンテンツパートが 200 個表示されること
　　　　　　・201 個目を追加して保存すると「コンテンツパートは200個まで設定できます。」と表示されること
　　　　　　・201 個目の保存に失敗した後もコンテンツパートが 200 個のまま残っていること
　　・デグレ確認
　　　・フロント 記事詳細 PC（/blog/{id}/detail）
　　　　・既存記事の表示
　　　　　・前提条件
　　　　　　・本対応のリリース前に作成された公開中の日本語の記事が存在すること
　　　　　　・対象記事にアイキャッチ画像・画像パート・関連作品が登録されていること
　　　　　・手順
　　　　　　・1. PC のブラウザで対象記事の記事詳細を開く
　　　　　　・2. ページを最下部までスクロールする
　　　　　・確認項目
　　　　　　・記事本文が表示されること
　　　　　　・画像パートの画像が表示されること
　　　　　　・アイキャッチ画像が表示されること
　　　　　　・関連作品が表示されること
```

## 注意

- 検証担当者は実装の内部事情を知らない前提で書く。「`ContentPartsDecoder` が null を返すこと」のような実装用語は使わず、画面で観測できる事象に翻訳する
- 1 項目に「〜と〜を確認する」と書かない。2 項目に分ける
- 期待結果が曖昧な表現（「正しく表示されること」）にならないよう、何をもって正しいかを書く
- デグレ確認の対象データは「**本対応のリリース前に作成された**記事」のように、いつ作られたものかを指定する
- 画質やレイアウトの確認は差が出やすい素材を前提条件で指定する。例：布の織り目や細かい格子などテクスチャが細かい写真
